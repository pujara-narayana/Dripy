────────────────────────────────────────
DECISIONS
────────────────────────────────────────

- Deploy only the website (Next.js on Vercel). The Photon iMessage worker is NOT deployed;
  for a live iMessage demo run `npm run worker` on a laptop, with DRIPY_BACKEND_URL pointing at
  the deployed site or localhost.
- Payments: Stripe test mode on the Visa test card (4242). Visa Intelligent Commerce dropped.
- After paying, Dripy emails an order receipt for the store, via the connected Gmail, to the
  buyer's sign-up address (to itself for the demo user Alex), and parses it into the wardrobe
  (same parser as real order emails). No "demo" labels in the email or the paid reply; it is
  sent as "<Store> via Dripy" and the footer says Dripy sent it (not the store).
- Verdicts only when asked ("should I buy this?"). Searches, photos and "buy it" get no
  BUY/SKIP/CONSIDER and no "you already own…" commentary.
- Demo vs. real run: for the demo, DEMO_CATALOG=true (curated bomber/blazer) and sign up with
  the connected Gmail; for a real run, DEMO_CATALOG=false (live Channel3) and any Gmail.
- Any store is allowed (no merchant allowlist). Checkout still needs a known store domain and
  an https product link, the user's YES, the $300 cap and the 10-minute expiry.
- Product search: Channel3 first, SerpAPI as fallback.
- Reply latency is not a priority.
- Dropped: Google Places (paid; Geoapify instead), WhatsApp (not enabled on the Photon
  project; Photon returns 403).

Added 2026-10-18 (Narayana):
- Buy links. iMessage lists the top 3 matches, each with its own product link; the verdict
  and checkout messages add the store link ("Rather check out yourself? <link>"); a URL is
  never repeated in one reply; the agent sees the links, so "send me the link" works.
- Channel3 product search (CHANNEL3_API_KEY): one image search + one text search per photo;
  every result is a real product page (via a buy.trychannel3.com tracking link) with the
  store's domain, price and stock. SerpAPI is the fallback; on that path the top 3 Google
  Shopping results are resolved to the store's own page.
- Demo receipt email (src/lib/pipelines/purchaseReceipt.ts): store-styled order confirmation,
  labeled "demo receipt" in subject, banner and footer, sent from the user's own Gmail to
  itself (needs the gmail.send scope: `npm run gmail:auth`). Falls back to an in-app receipt
  without Gmail, and to adding the item directly if parsing fails. The payment_confirmation
  card has `receipt: {retailer, emailed, wardrobe_item_ids}` for the website.
- iMessage no longer sends the "🧾 Ref … / 📧 receipt" message after paying (the reply says it).
- Agent asks which product when "buy it" is ambiguous. Bug found in testing: it recommended
  Zara but charged COS, because comparing COS made it the current product.
- Merchant allowlist removed (see Decisions).
- Buy-check fix: it no longer says SKIP just because you own 3+ items of that category for
  the same occasion (white linen trousers were SKIPped citing black chinos, beige shorts and
  jeans). SKIP now needs a real near-duplicate; shorts/skirts never count as duplicates of
  trousers/jeans; pants = trousers = slacks. The iMessage verdict names the item it judged.

Demo catalog: DEMO_CATALOG=true makes the black bomber / camel blazer always return the same
curated matches (repeatable SKIP / BUY), but their links are store SEARCH pages. With
DEMO_CATALOG=false (current .env.local) every photo uses live Channel3 results.

ADDED ON THE `frontend` BRANCH (2026-10-18)
────────────────────────────────────────

The web app and the end-to-end demo flow:
- Sign-up (name, Gmail, phone) → the page opens iMessage with a start code → Dripy links the
  phone and greets with "I've parsed your Gmail and your digital wardrobe is ready: <link>".
  The closet is a fixed Uniqlo starter closet (src/data/catalog.ts), not a real Gmail parse.
- Shop (Recommended page): catalog pieces the user doesn't own, shuffled.
- Visa checkout: the first purchase texts a signed /checkout/:id link with a Visa card form
  (only brand + last 4 kept); after that "Reply YES" or a one-tap Approve on the web.
- Donate from /donate: pieces leave the closet, the nearest drop-offs post to web chat and
  iMessage (worker POST /send).
- iMessage and web chat are one conversation: the agent now loads the last 40 messages (was
  12) with user messages tagged [iMessage] / [website chat], so the web agent can buy a
  product from a photo sent on iMessage.
- Receipts go to the sign-up address (see Decisions).
- next.config.ts allows *.trycloudflare.com as a dev origin, for phone testing through a
  Cloudflare quick tunnel (APP_URL=https://<random>.trycloudflare.com). README has the steps.

Tests (2026-10-18, frontend branch): typecheck, lint (only <img> warnings), npm test,
test:integrations (mocked and --live), smoke:stripe, smoke:gemini and test:contract (mock
mode, FORCE_FALLBACK=all) all pass. The live contract test was not run on purpose: it writes
to the shared demo user, runs a real Gmail sync and uses ~12 Gemini requests.

Not yet tested end to end over iMessage. First attempt: the start-code text went from an
Apple ID email, which Photon's shared number rejects ("can't route it to the right agent").
Send from the phone number (README section 4).

────────────────────────────────────────
WHAT IT WOULD TAKE FOR REAL USERS
────────────────────────────────────────

The core architecture holds up: the agent, the tools, the safe payment flow, the iMessage
bridge and the fallbacks. The gaps:

Area: Buying the item ⚠️ biggest gap
What's demo-only today: Stripe charges a test card and Dripy emails a demo receipt "from" the store, but nothing actually orders the item from the store
What real use needs: A way to actually complete the order: (a) send the user to the store to check out (simplest, and earns affiliate fees), (b) the newer agent-checkout
standards (Visa Intelligent Commerce, Stripe/OpenAI's Agentic Commerce Protocol, Shopify), which need each merchant to support them, or (c) Dripy buys on the user's
behalf, which means fulfillment, returns and money-transmission law
Effort: (a) days; (b) weeks plus partnerships; (c) months
────────────────────────────────────────
Area: Users and login
What's demo-only today: One hardcoded demo user. Any unknown phone number gets Alex's closet, which would leak data in production. user_id is a plain request parameter.
What real use needs: Sign-up by phone number, login for the web app, user identity taken from the session, and database-level security rules per user
Effort: 2–4 days
────────────────────────────────────────
Area: Saving cards
What's demo-only today: A test card attached automatically
What real use needs: Card entry in the app (Stripe's card form); handling banks that demand extra verification on background charges; refunds
Effort: 2–3 days
────────────────────────────────────────
Area: Getting the closet in
What's demo-only today: Gmail read-only works for one test user (refresh token in env, expires every 7 days in testing mode); otherwise 5 seeded emails; wear counts are seeded
What real use needs: Per-user Gmail OAuth with stored tokens, Google's paid security review for public users (weeks), Outlook, product photos, de-duplication, and a way to log
what you actually wear
Effort: 1–2 weeks, plus Google's review
────────────────────────────────────────
Area: Product results
What's demo-only today: Channel3 (product catalog API, 1,000 free calls/month, real product pages with affiliate links) with SerpAPI as fallback, plus 2 curated demo matches when DEMO_CATALOG=true
What real use needs: A paid Channel3 plan or licensed feeds (ShopStyle, Rakuten, Impact), live sizes, cost limits per user, a policy for which stores count as trustworthy (there is no store allowlist anymore)
Effort: Days
────────────────────────────────────────
Area: iMessage
What's demo-only today: Free plan, shared number; every user must be pre-registered; WhatsApp not enabled
What real use needs: Photon Business plan with a dedicated number (paid), opt-in and STOP handling, the worker running 24/7, a real single-worker lock (today it only checks a local port)
Effort: Days, plus cost
────────────────────────────────────────
Area: Reliability
What's demo-only today: Synchronous requests, no queue; a slow Gemini or Lens call makes the whole reply wait
What real use needs: A job queue with retries, model fallback, usage limits per user, monitoring and alerts
Effort: 3–5 days
────────────────────────────────────────
Area: Security and privacy
What's demo-only today: Image-URL fetch is now SSRF-safe; otherwise fine for a demo
What real use needs: Data deletion, a privacy policy, encryption of emails and purchase history, and a broader security review
Effort: 1 week
────────────────────────────────────────
Area: Donations
What's demo-only today: Geoapify (OpenStreetMap second-hand shops) + 5 seeded Seattle stores; charity chains only from the seeded list
What real use needs: A source with good charity/donation coverage and accurate hours (Google Places, paid), per-city data
Effort: 1 day
